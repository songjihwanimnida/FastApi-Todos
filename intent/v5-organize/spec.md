# Spec: v5.0.0 — 프로젝트, 하위 할 일, 반복, 검색·필터·정렬
Author: songjihwan. Date: 2026-11-17. Status: draft.
Intent: [intent.md](./intent.md)

## 요약
`todo.json` 에 프로젝트 목록을 추가하고, 할 일에 `project_id`, `subtasks`, `repeat` 세 필드를 더한다. `GET /todos` 는 쿼리 파라미터로 검색·필터·정렬을 하고, 쿼리가 없으면 지금과 똑같이 전체 목록을 준다. 반복 할 일의 다음 회차는 서버가 PUT 에서 "미완료 → 완료"로 바뀔 때 만든다. 화면은 왼쪽에 프로젝트 목록, 위쪽에 검색·필터·정렬 도구 막대가 생기고, 할 일 행에 하위 할 일과 반복 표시가 붙는다.

## 요구사항

### 공통·호환 (`fastapi-app/main.py`)
- **R1** 기존 호출은 그대로 동작한다. 제목만 보낸 `POST /todos` 는 201 이고, 쿼리 없는 `GET /todos` 는 저장된 순서(id 순) 그대로 전체를 준다.
- **R2** `todo.json` 의 v3 목록 형식과 v4 형식(`next_id` + `todos`)을 읽는다. 새 필드가 없는 할 일은 `project_id: null`, `subtasks: []`, `repeat: null` 이 된다. 프로젝트가 없는 파일은 프로젝트 0개다.
- **R3** 저장 형식은 `{"next_id", "next_project_id", "projects", "todos"}` 이다. 프로젝트 id 도 `next_project_id` 로 매기고 지운 id 를 다시 쓰지 않는다.
- **R4** 새 엔드포인트도 모두 `STORE_LOCK` 안에서 `load_store()` → 수정 → `save_store()` 한다.
- **R5** API 버전을 `5.0.0` 으로 올린다.

### 프로젝트
- **R6** 프로젝트는 `{id, name}` 이다. `name` 은 앞뒤 공백을 지운 뒤 1~30자, strict 검증.
- **R7** `GET /projects` 는 id 순 전체 목록, `POST /projects` 는 201, `PUT /projects/{id}` 는 이름 변경(200), `DELETE /projects/{id}` 는 204. 없는 id 는 404.
- **R8** 같은 이름(앞뒤 공백 제거 후, 대소문자 무시)의 프로젝트는 만들거나 그 이름으로 바꿀 수 없다 → 409. 자기 이름을 그대로 다시 저장하거나 대소문자만 바꾸는 것은 허용한다.
- **R9** 프로젝트를 삭제하면 `project_id` 가 그 프로젝트인 할 일을 한 번의 저장으로 함께 지운다.
- **R10** 할 일의 `project_id` 는 정수 또는 `null`(수집함)이다. `POST`/`PUT` 에서 없는 프로젝트 id 를 보내면 422 이고 저장하지 않는다.

### 하위 할 일
- **R11** `subtasks` 는 `{title, completed}` 목록이다. `title` 은 공백 제거 후 1~100자, `completed` 기본값 `false`, strict 검증. 할 일 하나에 최대 50개. 기본값은 `[]`.
- **R12** 하위 할 일은 별도 id 나 엔드포인트가 없다. 추가·체크·삭제·순서는 할 일 PUT(전체 교체)으로 목록 전체를 보내 바꾼다.
- **R13** 하위 할 일을 모두 체크해도 할 일이 자동으로 완료되지 않고, 할 일을 완료해도 하위 할 일은 바뀌지 않는다.

### 반복 할 일
- **R14** `repeat` 는 `"daily"`, `"weekly"`, `"monthly"`, `null` 중 하나다. `repeat` 가 있는데 `due_date` 가 `null` 이면 422.
- **R15** `PUT /todos/{id}` 에서 저장돼 있던 할 일이 미완료이고, 요청이 `completed: true` 이면서 `repeat` 가 있으면 다음 회차를 새로 만든다. 새 할 일은 `next_id` 로 id 를 받고, 제목·설명·우선순위·프로젝트·반복을 그대로, 하위 할 일은 모두 `completed: false` 로, `completed: false`, `due_date` 는 다음 날짜로 한다.
- **R16** 다음 날짜는 원래 `due_date` 기준이다. 매일 +1일, 매주 +7일, 매월은 다음 달 같은 날이며 그 달에 없는 날이면 말일로 맞춘다(1/31 → 2/28). 다음 날짜가 9999-12-31 을 넘으면 다음 회차를 만들지 않는다.
- **R17** 다음 회차를 만들면, 완료한 할 일 쪽의 `repeat` 는 `null` 로 저장한다. 반복은 새 회차가 이어받는다. 그래서 완료를 해제했다가 다시 완료해도 회차가 또 생기지 않는다. PUT 응답은 완료한 할 일(`repeat: null`)이다.
- **R18** POST 로 처음부터 `completed: true` 인 반복 할 일을 만들거나, 이미 완료된 할 일을 다시 완료로 PUT 하면 다음 회차를 만들지 않는다.

### 검색·필터·정렬 (`GET /todos` 쿼리)
- **R19** `q`: 앞뒤 공백을 지운 뒤, 제목이나 설명에 대소문자 무시로 포함되면 남긴다. 빈 값은 거르지 않는다.
- **R20** `project_id`: 정수. `0` 은 수집함(`project_id` 가 `null` 인 할 일), 그 밖은 해당 프로젝트. 없는 프로젝트 id 면 빈 목록. 음수는 422.
- **R21** `priority`: 1~4 정수 하나. 범위 밖이나 정수가 아니면 422.
- **R22** `status`: `open`(미완료), `done`(완료). 생략하면 둘 다. 다른 값은 422.
- **R23** `sort`: `created`(id 순, 기본값), `priority`(우선순위 → id), `due`(마감일 빠른 순, 마감일 없는 할 일은 뒤로 → 우선순위 → id), `title`(제목 대소문자 무시 → id). 다른 값은 422.
- **R24** 조건은 모두 AND 로 묶는다. "기한 지남"은 API 에 없다(서버는 오늘 날짜를 모른다, intent).

### 화면 (`fastapi-app/templates/index.html`)
- **R25** 왼쪽 사이드바에 "전체", "수집함", 프로젝트 목록(이름 + 미완료 개수)과 "프로젝트 추가"를 둔다. 고른 항목은 `aria-current="page"` 다. 화면 너비 767px 이하에서는 사이드바 대신 제목 옆 선택 상자(`<select>`, 라벨 "프로젝트")로 고른다.
- **R26** 프로젝트를 고르면 제목, 개수, 진행률이 그 프로젝트 기준으로 바뀐다. 진행률은 검색·필터와 상관없이 고른 범위 전체로 계산한다.
- **R27** 프로젝트 화면 제목 옆에 "이름 바꾸기", "삭제" 버튼을 둔다. 삭제 확인 창에 `"업무"와 할 일 5개가 삭제됩니다` 처럼 함께 지워질 개수를 보여준다. 409 이면 "같은 이름의 프로젝트가 있습니다"를 알린다.
- **R28** 도구 막대: 검색칸(라벨 "검색", 입력 후 250ms 뒤 요청), 우선순위 필터(전체/1~4), 상태 필터(전체/진행 중/완료/기한 지남), 정렬(우선순위/추가순/마감일/제목, 기본 우선순위). 조건이 하나라도 걸려 있으면 "필터 지우기" 버튼이 보인다.
- **R29** 상태 필터가 "전체"면 지금처럼 미완료 목록 + 접이식 "완료됨" 섹션이다. "진행 중"이면 완료됨 섹션을 숨기고, "완료"면 완료한 할 일만 목록으로 보인다. "기한 지남"은 `status=open` 으로 받은 결과에서 화면이 `isOverdue` 로 거른다.
- **R30** 조건에 맞는 할 일이 없으면 "조건에 맞는 할 일이 없습니다" 상태와 "필터 지우기" 버튼을 보여준다. 할 일이 아예 없을 때의 기존 문구와 구분한다.
- **R31** 고른 프로젝트와 검색·필터·정렬 값을 주소 쿼리(`?project=3&q=보고서&sort=due`)에 반영해, 새로고침하거나 주소를 공유해도 같은 화면이 나온다. 없는 프로젝트 id 가 주소에 있으면 "전체"로 돌아간다.
- **R32** 추가·편집 폼에 프로젝트 선택(라벨 "프로젝트", 수집함 + 프로젝트들), 반복 선택(라벨 "반복", 안 함/매일/매주/매월), 하위 할 일 편집(목록 + "하위 할 일 추가" 입력칸, 항목별 삭제)을 둔다. 프로젝트 화면에서 추가하면 그 프로젝트가 미리 골라져 있다.
- **R33** 마감일이 비어 있으면 반복 선택을 비활성화하고 "안 함"으로 둔다. 마감일을 지우면 반복도 "안 함"이 된다(R14 의 422 를 화면에서 미리 막음).
- **R34** 할 일 행: 하위 할 일이 있으면 `2/5` 진행 표시와 펼치기 버튼이 보이고, 펼치면 하위 할 일마다 체크 버튼(`role="checkbox"`, 이름 `하위 할 일 <제목> 완료`)이 있다. 반복이면 반복 아이콘과 "매주" 같은 글자가 보인다. "전체" 화면에서는 프로젝트 이름도 보인다. 펼침 상태는 다시 그려도 유지한다.
- **R35** 화면이 보내는 모든 할 일 PUT 은 `project_id`, `subtasks`, `repeat`, `due_date` 를 빠짐없이 담는다(완료 체크, 하위 할 일 체크, 편집 모두).
- **R36** 반복 할 일을 완료하면 "다음 회차를 2026년 11월 24일로 만들었습니다" 토스트를 띄운다(응답 전후 목록의 차이로 판단하지 않고, 완료 전 할 일의 `repeat`·`due_date` 로 다음 날짜를 계산해 보여준다 — 계산은 R16 과 같은 규칙).
- **R37** 기존 마감일 동작(R9–R17 of due-date spec: 기한 지남 표시, 접근성 이름, `badInput` 차단, 탭 복귀 시 다시 그리기)과 기존 UI 테스트 `test_due_date_ui.py` 가 그대로 통과한다.

## 설계

**모델**
```python
Repeat = Literal["daily", "weekly", "monthly"]

class SubtaskIn(BaseModel):          # strict, str_strip_whitespace
    title: str = Field(min_length=1, max_length=100)
    completed: bool = False

class TodoIn(BaseModel):             # 기존 필드 + 아래 3개
    project_id: int | None = None
    subtasks: list[SubtaskIn] = Field(default_factory=list, max_length=50)
    repeat: Repeat | None = None
    # model_validator: repeat 가 있으면 due_date 필수 (R14)

class ProjectIn(BaseModel):          # strict, str_strip_whitespace
    name: str = Field(min_length=1, max_length=30)

class ProjectItem(ProjectIn):
    id: int

class TodoStore(BaseModel):
    next_id: int = 1
    next_project_id: int = 1
    projects: list[ProjectItem] = []
    todos: list[TodoItem] = []
    # next_id_after_max 를 프로젝트에도 똑같이 적용
```
- `project_id` 존재 확인(R10)은 저장된 프로젝트 목록이 필요하므로 모델이 아니라 엔드포인트에서 `STORE_LOCK` 안에서 한다. 422 의 `detail` 은 FastAPI 검증 오류와 같은 모양(`[{"loc": ["body", "project_id"], "msg": ..., "type": "project_not_found"}]`)으로 맞춰, 클라이언트가 한 가지 방식으로 처리할 수 있게 한다.
- 다음 날짜 계산은 순수 함수 `next_due(due: date, repeat) -> date | None` 로 분리한다(`calendar.monthrange` 로 말일 계산, 표준 라이브러리만). `None` 은 9999년을 넘는 경우(R16).
- 쿼리 파라미터는 `Annotated[..., Query(...)]` 로 선언해 Swagger 에 설명이 나오게 한다. `sort`·`status` 는 `Literal`.

**API 예시**
```json
// POST /projects  →  201
{"name": "업무"}
{"id": 1, "name": "업무"}

// POST /todos  →  201
{"title": "주간 보고", "project_id": 1, "due_date": "2026-11-20", "repeat": "weekly",
 "subtasks": [{"title": "숫자 정리"}, {"title": "메일 보내기"}]}
{"id": 7, "title": "주간 보고", "description": "", "completed": false, "priority": 4,
 "due_date": "2026-11-20", "project_id": 1, "repeat": "weekly",
 "subtasks": [{"title": "숫자 정리", "completed": false}, {"title": "메일 보내기", "completed": false}]}

// PUT /todos/7 (completed: true, 나머지 그대로)  →  200, 응답은 repeat: null
// 이후 GET /todos 에 id 8, due_date "2026-11-27", repeat "weekly", 하위 할 일 체크 해제된 새 회차가 생김

// GET /todos?project_id=1&status=open&sort=due&q=보고
```

**화면 상태**
- `state` 에 `projects`, `all`(쿼리 없는 전체 목록 — 사이드바 개수·진행률·삭제 확인 개수용), `todos`(쿼리 결과 — 목록용), `view: {project, q, priority, status, sort}`, `expanded: Set<id>` 를 둔다.
- `load()` 는 `GET /projects`, `GET /todos`, `GET /todos?<view>` 세 요청을 `Promise.all` 로 보낸다. `view` 가 비어 있으면 세 번째 요청은 생략하고 `all` 을 쓴다.
- 검색어 입력 중 늦게 도착한 옛 응답이 새 결과를 덮지 않도록 요청마다 번호를 매기고 마지막 번호의 응답만 반영한다.
- 할 일 PUT 본문은 한 곳(`todoBody(todo, changes)`)에서 만든다. 기존 할 일의 모든 필드를 펼친 뒤 바뀐 값만 덮어서, 필드가 늘어도 빠뜨리지 않는다(R35).
- 화면의 다음 날짜 계산 `nextDue(due, repeat)` 도 문자열로만 계산한다(`Date` 파싱 금지 규칙 유지). 말일은 `new Date(y, m, 0).getDate()` 처럼 숫자 인자로만 구한다.

## 제약 조건 충족 방식

| intent 제약 조건 | 충족 방법 | 요구사항 | 검증 |
|---|---|---|---|
| 기존 API 호출이 깨지지 않음 | 새 필드는 모두 기본값이 있는 선택 필드, `sort` 기본값 `created` 는 지금 순서와 같음 | R1, R23 | 기존 단위 테스트 전부 통과(`test_create_todo` 기대값만 새 필드 추가), JMeter 계획(POST 제목+설명, GET) 그대로 실행 |
| v3·v4 `todo.json` 읽기 | 새 필드·`projects`·`next_project_id` 모두 기본값 | R2 | `test_legacy_list_format`, `test_v4_file_without_due_date` 유지 + v4.2 형식 파일 읽기 테스트 |
| PUT 전체 교체 유지, 화면은 빠짐없이 보냄 | API 는 그대로, 화면은 `todoBody` 한 곳에서 본문 생성 | R12, R35 | 단위 테스트(생략하면 기본값), UI 테스트(체크 후 API 값 유지) |
| strict 검증을 새 필드에도 | 새 모델 모두 `strict=True` | R6, R11, R14 | 422 parametrize 에 새 경우 추가 |
| 없는 프로젝트 id, 마감일 없는 반복 거부 | 엔드포인트 존재 확인, 모델 검증기 | R10, R14 | 단위 테스트 |
| `STORE_LOCK`, `next_id`, 지운 id 재사용 금지 | 프로젝트도 `next_project_id`, 모든 엔드포인트 잠금 | R3, R4 | `test_concurrent_requests` 에 프로젝트 생성·반복 완료를 섞은 동시 테스트 |
| 새 의존성 없음, `/metrics` 유지 | `calendar`·`typing` 표준 라이브러리만 | — | `requirements.txt` diff 없음, `test_metrics_endpoint` |
| 날짜는 문자열, 색만으로 구분하지 않음 | 화면의 `nextDue` 도 문자열 계산, 반복·하위 진행은 글자로 표시 | R34, R36 | UI 테스트가 글자와 접근성 이름 확인 |

## Open questions

1. **매월 반복의 말일 처리 — intent 의 제안과 다름, 확인 필요.** intent 에는 "1/31 → 2/28 → 3/31" 로 적었다. 그런데 2/28 다음을 3/31 로 하려면 "원래 31일이었다"는 것을 어딘가 저장해야 한다(필드 추가 → PUT 전체 교체에서 화면이 또 하나 빠짐없이 보내야 하고, API 사용자에게도 노출됨). 이 spec 은 **필드를 추가하지 않고 "1/31 → 2/28 → 3/28"** 로 정했다(R16). 말일에 맞춰야 하는 일이 중요하면 `repeat_day` 필드를 추가하는 쪽으로 바꾼다.
2. **반복 완료 해제** — 결정: 다음 회차는 그대로 두고, 완료한 쪽은 `repeat: null` 이 된다(R17). intent 의 제안("이미 만든 다음 회차는 그대로")과 같고, 다시 완료해도 회차가 겹치지 않는다.
3. **프로젝트 이름 중복** — 결정: 대소문자 무시 중복 거부 409 (R8).
4. **수집함을 쿼리로 나타내는 방법** — 결정: `project_id=0` (R20). 프로젝트 id 는 1부터라 겹치지 않는다. Swagger 설명에 적는다.

## Areas of concern

**1. PUT 전체 교체 때문에 하위 할 일·반복·프로젝트가 조용히 지워진다.**
지금 가장 위험한 부분이다. 필드를 모르는 클라이언트(캐시된 v4 `index.html`, Swagger 에서 제목만 넣은 PUT, 스크립트)가 PUT 하면 하위 할 일 목록이 통째로 사라지고 프로젝트에서 빠지고 반복이 꺼진다. 하위 할 일은 사용자가 손으로 입력한 데이터라 마감일보다 잃었을 때 아프다. API 는 intent 대로 전체 교체를 유지하고, 화면은 `todoBody` 한 곳에서 본문을 만든다. 배포 직후 브라우저에 옛 `index.html` 이 남아 있으면 위험하므로, 릴리즈 노트에 "업데이트 후 새로고침"을 적는다. 탭 두 개 문제(마지막 쓰기가 이김)는 그대로다.

**2. 반복 회차 생성이 "이전 상태"에 의존한다.**
R15 는 저장된 값과 요청 값을 비교하므로 반드시 잠금 안에서 읽은 값으로 판단해야 한다. 같은 할 일에 완료 PUT 이 동시에 두 번 오면(더블 클릭, 탭 두 개) 잠금 덕분에 두 번째는 이미 완료 상태를 보고 회차를 만들지 않는다. 동시 테스트로 확인한다.

**3. 프로젝트 삭제는 되돌릴 수 없고 여러 할 일을 지운다.**
intent 에서 "함께 삭제"로 정했다. 확인 창의 개수는 화면이 가진 `all` 로 계산하므로, 다른 탭에서 방금 추가한 할 일은 개수에 빠질 수 있다. 서버는 삭제 시점의 파일 기준으로 지우므로 데이터가 어긋나지는 않는다.

**4. 화면 요청이 늘어난다.**
`load()` 가 최대 3번 GET 하고, 매번 `todo.json` 전체를 읽는다. 지금 규모(할 일 수백 개)에서는 문제없지만 JMeter 결과(응답 시간)에는 영향이 없다 — JMeter 계획은 화면을 거치지 않는다. 검색은 250ms 디바운스와 최신 응답만 반영으로 요청 수와 순서 문제를 막는다.

**5. 롤백하면 데이터가 사라진다.**
v4.2.0 코드로 되돌리면 모르는 필드를 무시하고 읽어서 앱은 동작하지만, 다음 저장 때 **프로젝트, 하위 할 일, 반복이 모두 사라진다**(프로젝트에 있던 할 일은 남고 수집함 상태가 됨). 릴리즈 노트의 업그레이드 참고에 "되돌리기 전에 `todo.json` 백업"을 적는다.

**6. 화면 구조가 크게 바뀌어 기존 UI 테스트가 깨질 수 있다.**
`test_due_date_ui.py` 는 `get_by_label("마감일", exact=True)`, 체크 버튼 이름, "할 일 추가" 버튼, "완료됨" 섹션에 의존한다. 새 폼의 라벨("반복", "프로젝트", "하위 할 일 추가")이 "마감일"과 겹치지 않게 하고, 체크 버튼 이름 형식을 바꾸지 않는다(R37). 하위 할 일 체크 버튼 이름은 `하위 할 일 …` 로 시작해 할 일 체크 버튼과 이름이 겹치지 않게 한다.

**7. 화면의 다음 날짜 계산이 서버와 어긋날 수 있다.**
R36 토스트는 화면이 계산한 날짜다. 서버(`next_due`)와 화면(`nextDue`)이 같은 규칙인지 UI 테스트에서 말일 경우(1/31 매월)로 확인한다. 어긋나면 토스트만 틀리고 데이터는 서버 기준이다.

**8. 주소 쿼리에 남은 값.**
삭제된 프로젝트 id 나 잘못된 `sort` 가 주소에 남아 있을 수 있다. 화면은 알 수 없는 값을 기본값으로 바꾸고 주소도 고친다(R31). 그대로 API 에 보내면 422 로 목록 전체가 "불러오지 못함"이 된다.

**9. `todo.json` 이 git 에 올라가 있다.**
처음 저장할 때 `next_project_id`, `projects` 와 모든 할 일의 새 필드가 붙어 큰 diff 가 생긴다. 커밋에 섞지 않는다. UI 테스트용 프로젝트는 이름을 `[UI테스트 …]` 로 시작해 정리 대상에 넣는다.
